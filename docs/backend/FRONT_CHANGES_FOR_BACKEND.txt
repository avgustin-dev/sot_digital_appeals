Что поменять на бэкенде
=======================
Дата: 19.08.2026
Платформа: приём граждан руководством Верховного суда КР
(фронт уже изменён; слоты и контент при NEXT_PUBLIC_API_URL считает бэкенд)


1. Личный график руководства — своё время на каждый день
--------------------------------------------------------
Раньше: leadership[].weekdays[] + одно startMinutes / endMinutes на все дни.

Теперь в CMS и в JSON контента:

  leadership[].windowKind = "fixed"   // личный график
  leadership[].dayWindows = [
    { "weekday": 4, "startMinutes": 540, "endMinutes": 720 },
    { "weekday": 2, "startMinutes": 900, "endMinutes": 960 }
  ]

weekday — как в JavaScript Date.getDay() / date-fns:
  0 = воскресенье, 1 = понедельник, …, 4 = четверг, 6 = суббота.

startMinutes / endMinutes — минуты от полуночи (09:00 = 540, 12:00 = 720).

Старые поля weekdays + одно startMinutes/endMinutes оставляем для совместимости.
Если dayWindows пустой — можно развернуть старые поля в окна «одно время на каждый weekday».

Нужно:
- GET /public/bootstrap и GET/PUT /staff/content — сохранять и отдавать dayWindows как есть (не отбрасывать поле).
- GET /public/slots и расчёт занятости:
    для targetId руководства с windowKind=fixed брать окно ТОГО дня недели, на который запрошена дата.
    Пример: вторник 15:00–16:00, четверг 09:00–12:00 — слоты на эти дни разные.
    Нельзя резать все дни одним startMinutes/endMinutes с карточки.
- windowKind=calendar — дни и часы только из календаря платформы
  (receptionWeekdays, dayStartMinutes, dayEndMinutes).
- Публичный график на сайте (день / время) фронт считает из dayWindows или из календаря.
  Поля weekdayRu/timeRu можно заполнять тем же текстом, но источником истины являются окна.


2. После завершения записи — оценка сервиса
-------------------------------------------
Когда запись завершена (appointment.status = completed) или обращение
на этапе reception_done / in_control / answered / closed,
фронт переводит гражданина на:

  /service-evaluation/{code}

PIN в эту ссылку не входит.

Нужно:
- После POST завершения приёма (completeReception) и при смене статуса записи на completed
  слать уведомление (SMS / e-mail / system) со ссылкой:
  {публичный_origin}/service-evaluation/{code}
- Не требовать PIN для открытия страницы оценки.
- Принимать POST оценки, если обращение не cancelled.
- Если оценка уже есть — повторная отправка обновляет её (фронт это умеет).


3. Статусы поручения (контроль)
-------------------------------
API-коды не менять:

  open | in_progress | done | overdue

На экране фронт показывает по-русски / по-кыргызски
(«К исполнению», «В работе», «Исполнено», «Просрочено»).
Не отдавать эти английские слова как единственную подпись в письмах гражданину —
в тексте уведомлений лучше сразу русские/кыргызские формулировки.


4. PDF-отчёт аналитики
----------------------
«Скачать отчёт (PDF)» делается на фронте (печать браузера).
Отдельный backend-эндпоинт PDF не обязателен.
Если позже понадобится серверный PDF — это отдельная задача.


5. QR талона
------------
QR рисуется на фронте (SVG). В QR только ссылка на статус:

  {origin}/appointment-status?code={CODE}

PIN в QR нет. С бэкенда картинку QR генерировать не нужно.


Проверка
--------
1) В CMS у председателя личный график: Чт 09:00–12:00 и отдельно Вт 15:00–16:00.
   Сохранить контент. GET bootstrap — в JSON есть dayWindows с двумя окнами.
2) GET слотов на ближайший четверг — окно 09:00–12:00.
   GET слотов на ближайший вторник того же лица — 15:00–16:00.
3) После completeReception гражданин по коду попадает на /service-evaluation/{code}.
4) В письме/SMS после приёма — эта же ссылка, без PIN.
